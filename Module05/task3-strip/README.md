# Task 3 — 8-pixel WS2812B strip

An 8-pixel addressable strip driven over one data line, with a serial
`index R G B` REPL and a power budget.

## Experimental report and photographic evidence

See the [English experiment report](experiment-report.md) for six unmodified
original photographs, the observed pixel arrangements, and the meter readings.
The photographed program banner shows luminance 96; the archived source below
uses 80. Meter displays of 0.8, 2.7, and 16.0 are in **mV**, not mA.
Current measurements remain unverified without documented measurement nodes
and any required shunt resistance.

## Wiring

| Strip pad | Goes to | Note |
|---|---|---|
| `VDC` | board **5V** | the strip needs 5 V, not 3V3 |
| `GND` | board **GND** | ground must be shared with the board |
| `DIN` | **GPIO 13** | data in; the `DOUT` end stays unconnected |

Connect in the order GND, then DIN, then VDC, and only while the board is
unpowered. Never plug or unplug the strip while it is powered — that is the usual
way to destroy the first LED.

Data is unidirectional: it must enter at the `DIN` end of the strip. Wired to
`DOUT` instead, no pixel lights at all.

**Pin deviation.** The course module specifies GPIO 16. This board does not break
out GPIO 16, so the data line is on **GPIO 13**, which also carried Task 1's LED
and Task 2's red channel. Unplug those before wiring the strip.

The 330 ohm series resistor the module mentions is optional insurance and is not
fitted here; it is not required for a short strip.

## Driver choice

`NeoPixelBusLg<NeoGrbFeature, NeoEsp32Rmt0Ws2812xMethod, NeoGammaNullMethod>`

- **`NeoGrbFeature`** — the strip's wire order is GRB, not RGB.
- **`NeoEsp32Rmt0Ws2812xMethod`** — the 800 kHz NRZ waveform is generated by the
  RMT peripheral in hardware, reducing software-timing dependence. Channel 0
  is selected here. The library also offers I2S methods for appropriate ESP32
  targets. No Wi-Fi/BLE stress test is archived; hardware offload does not
  establish immunity to all faults. A legacy-driver warning was reported.
- **`NeoPixelBusLg`** rather than `NeoPixelBus`, because only the Lg class has
  `SetLuminance()`. It has its own header: `#include <NeoPixelBusLg.h>`.

## Commands

| Input | Effect |
|---|---|
| `0 255 0 0` | pixel 0 red |
| `7 0 0 255` | pixel 7 blue |
| `3 255 255 255` | pixel 3 white |
| `clear` | every pixel off |
| `all 255 255 255` | every pixel white, subject to luminance cap |
| `8 255 0 0` | rejected: index out of bounds |
| `0 256 0 0` | rejected: value out of range |
| `0 255 0` | rejected: needs index plus three values |

Each accepted command echoes `applied index=… R=… G=… B=…`, so the serial log is
its own evidence.

```sh
cd Module05/task3-strip

```

## Power budget

Cost model: up to 60 mA per pixel at full white (20 mA per colour channel), so
`n × 60 mA`. `SetLuminance(80)` scales the duty to roughly 80/255 of that.

| Pixels | Full white, computed | At luminance 80, computed | Measured |
|---|---|---|---|
| 8 | 480 mA | ≈151 mA | Not measured |
| 30 | 1.80 A | ≈565 mA | Not measured |
| 60 | 3.60 A | ≈1.13 A | Not measured |
| 144 | 8.64 A | ≈2.71 A | Not measured |

The nominal 500 mA USB planning budget leaves only 20 mA after the modelled
480 mA full-white strip load, before adding the board. The luminance cap adds
headroom but is not proof that a particular port is adequate. Check the actual
port/supply rating; a USB-C connector alone does not guarantee available current.
The proportional estimates omit idle current and are not electrical measurements.

See the shared [power table and supply decision](../README.md#strip-power-budget--computed-versus-measured) for model assumptions and measurement limitations.
